Slide 3 Defense Guide

🎯 Spoken Presentation Pitch (Say This to the Presenters / Jury)

"MediKiosk is a React and FastAPI prototype that guides patients through a nine-stage multispecialty intake, routes consultation requests to a doctor workstation, and offers consent-aware demonstration record viewing. Its FHIR R4 output is an example bundle; the prototype has no live ABHA or ABDM connection."

"This is not a clinical deployment: backend endpoints do not enforce authenticated, doctor-specific authorization, and the report viewer cannot prevent screenshots or other capture. Do not enter real patient data."

⚡ Technology-by-Technology Cross-Examination & Rapid Defense

📱 1. Mobile / Kiosk / Tablet Patient Intake Layer
❓ Jury: "Why dual hardware (Kiosks + Mobile)? Wouldn't a mobile app be enough?"
Defense: In high-volume Indian government OPDs, many rural or elderly patients either lack smartphones or have low data/battery. The physical touch-and-voice kiosk accommodates walk-ins immediately upon arrival, while QR-code mobile intake offloads queue congestion for tech-savvy smartphone users.
❓ Jury: "How will rural, illiterate patients navigate a touch screen?"
Defense: The intake is voice-first and iconography-driven. Large pictorial tap buttons with bilingual audio read-aloud enable patients to simply speak into the microphone or tap intuitive pictorial options without reading text.
⚛️ 2. React / React Native Frontend & Kiosk Web App
❓ Jury: "Why React over Flutter or native Android?"
Defense: React and React Native share over 75% of state management, business logic, and bilingual i18n translation schemas. React PWA deploys instantly inside embedded Chromium kiosk displays without waiting for mobile app store approvals, while React Native provides smooth tablet performance.
❓ Jury: "How do you handle heavy DOM re-renders with live polling queues and complex FHIR JSON?"
Defense: We isolate state using selective state slicing and memoization (useMemo, useCallback). The 6-second polling queue updates only the sidebar badge without triggering re-renders of the physician's active consultation canvas.
🐍 3. Python + FastAPI Asynchronous Backend & AI Processing
❓ Jury: "Why FastAPI instead of Node.js Express or Django?"
Defense: FastAPI is built natively on Starlette and Pydantic, delivering ASGI asynchronous non-blocking throughput comparable to Go and Node.js. Furthermore, Python is the native ecosystem for AI/ML (LangChain, Hugging Face, OCR, vision libraries), avoiding external process serialization bottlenecks.
❓ Jury: "Python has the Global Interpreter Lock (GIL). How will it scale to 10,000 OPD patients?"
Defense: Our API operations are heavily I/O-bound (LLM requests, database queries, ABDM network calls), which release the GIL under asyncio. For CPU-intensive image preprocessing, we dispatch jobs to asynchronous background Celery/Redis workers scaled horizontally across Docker containers.
🧠 4. LLM + RAG Adaptive Questions & Clinical Summaries
❓ Jury: "What if the LLM hallucinates a wrong diagnosis or dangerous medicine?"
Defense: We enforce an architectural Strict Non-Diagnostic Mandate. The LLM is strictly prohibited from generating disease labels or pharmacological prescriptions—it acts purely as a clinical scribe synthesizing reported symptoms and timelines. The doctor is legally and functionally the sole diagnostician.
❓ Jury: "Why RAG? Why not just use a system prompt?"
Defense: RAG grounds the LLM in verified clinical frameworks—the clinical SOCRATES pain analysis protocol, ICMR guidelines, and Charaka Samhita Dashavidha Pariksha standards. This prevents open-ended generation and ensures standardized medical structuring.
🎙️ 5. Speech AI (STT + TTS) Multilingual Voice Conversation
❓ Jury: "How do you handle Indian accents, noisy OPD waiting halls, and Hinglish?"
Defense: We deploy directional noise-cancelling hardware with spectral subtraction preprocessing. In software, our prompt engine handles bilingual code-switching (Hinglish) by mapping colloquial terms (e.g. 'pet me jalan', 'chakkar aana') directly to standardized medical terms (SNOMED CT / NAMASTE portal).
❓ Jury: "What speech engine powers this?"
Defense: A tiered architecture: client-side Web Speech API for low-latency zero-cost edge synthesis, with cloud fallback to Government of India's AI4Bharat Bhashini APIs and OpenAI Whisper for regional dialect accuracy.
📄 6. PaddleOCR / Tesseract Medical Document Digitization
❓ Jury: "Doctor handwriting is notoriously illegible. Can your OCR actually read it?"
Defense: We use a hybrid pipeline: PaddleOCR detects word bounding boxes, which are fed to vision-language models constrained by a standardized Indian pharmacopeia dictionary (both Allopathic & Ayurvedic formulations). Unclear words with <85% confidence are flagged in extraction_notes for physician review rather than hallucinated.
❓ Jury: "Why PaddleOCR over pure Tesseract?"
Defense: PaddleOCR significantly outperforms Tesseract on Devanagari script, curved prescription lines, and low-light mobile photos captured in rural health centers.
🐘 7. PostgreSQL Structured Patient Records
❓ Jury: "Why PostgreSQL instead of MongoDB if medical records are JSON?"
Defense: PostgreSQL delivers ACID compliance and relational integrity for patient identity, token sequences, and audit logs, combined with native JSONB and GIN indexing for flexible semi-structured clinical case sheets.
❓ Jury: "How do you avoid duplicate token numbers during high-concurrency rush hours?"
Defense: We use database-level atomic sequences and row-level locking (SELECT FOR UPDATE), ensuring gapless, sequential token allocation even if multiple bookings hit the server simultaneously.
🌐 8. FHIR / ABDM APIs Interoperable National Health Records
❓ Jury: "What ABDM milestones and FHIR resources are implemented?"
Defense: No ABDM milestones or ABHA integration are implemented in this prototype. The application generates a demonstration FHIR R4 bundle; production conformance has not been certified.
🔒 9. Prototype Security Limitations Security, Privacy & Access Control
❓ Jury: "What security controls are available, and what remains open?"
Defense: The demo includes a patient-controlled consent toggle and locks the in-app viewer after sharing is revoked. However, backend authorization, secure server sessions, encryption guarantees, and audit logging are not implemented. The role check is client-side only; do not use real patient data.
